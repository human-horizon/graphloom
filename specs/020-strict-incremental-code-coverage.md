# Строгая пошаговая разметка кода с контролем покрытия

## Контекст

Текущий анализатор создаёт сущности только для части AST: вызовов внутренних функций, условий, циклов и возвратов. Присваивания, стандартные вызовы и другие исполняемые конструкции могут исчезнуть из диаграммы. Промпты также разрешают ИИ пропускать «тривиальные» строки. В результате диаграмма не доказывает, что весь код разобран.

ИИ должен иметь право объединять соседние строки в один осмысленный блок, но ни одна строка исполняемого кода не должна оставаться без блока. Сложные блоки должны рекурсивно раскладываться на подблоки.

## Цель

Построить строгий инкрементальный pipeline: анализатор формирует детерминированный реестр всех исполняемых конструкций, ИИ обрабатывает код последовательными окнами, а валидатор не принимает результат с пропусками, пересечениями или неподтверждёнными диапазонами.

## Границы покрытия

- Обязательному покрытию подлежат все непустые строки с исполняемым кодом и все AST-конструкции внутри них: присваивания, вызовы, условия, циклы, `switch`, `return`, `break`, `continue`, объявления локальных переменных и другие поддержанные конструкции Go/TypeScript.
- Пустые строки, комментарии и форматирующие закрывающие скобки не являются отдельными шагами.
- Многострочная конструкция считается одной AST-единицей, но покрывает весь свой диапазон строк.
- Несколько конструкций на одной строке получают разные стабильные AST-идентификаторы.
- Родительский составной блок может охватывать диапазон потомков, но непосредственные AST-единицы одного уровня должны быть покрыты ровно один раз.

## Что изменится

1. `analyzers/go/internal/analyzer/entities.go` — выдавать полный реестр исполняемых AST-единиц с точными диапазонами, родителями и исходным текстом.
2. `analyzers/ts/src/analyzer.ts` и `analyzers/ts/src/entities.ts` — добавить такой же реестр для TypeScript/TSX.
3. `src-tauri/src/ucm.rs` — расширить контракт сущности данными покрытия и исходным фрагментом кода.
4. `src-tauri/src/semantic.rs` — строить дерево без потери AST-единиц и поддерживать рекурсивные составные блоки.
5. `src-tauri/src/pipeline.rs` — реализовать очередь окон, накопительный реестр покрытия и строгую валидацию перед сохранением отчёта.
6. `src-tauri/src/llm.rs` и `src-tauri/prompts/*.md` — добавить протокол последовательной разметки, маркеры уже обработанных диапазонов, обязательные русские `label` и `summary`.
7. `src-tauri/src/dsl.rs` и `src-tauri/src/dsl.schema.json` — хранить покрытые AST-идентификаторы/диапазоны и признак необходимости декомпозиции.
8. `src-tauri/src/validate.rs` — отклонять DSL с пропущенными, лишними или пересекающимися единицами покрытия.
9. `src-tauri/src/render.html` — показывать объединённые блоки и их рекурсивные подблоки без потери source navigation.
10. `src-tauri/src/render.rs` и тестовые fixtures — проверить новый контракт и строгие ошибки.

## Детали реализации

### 1. Детерминированный реестр

Анализатор передаёт для каждой области исходника упорядоченный список `CoverageUnit`:

- стабильный `id`;
- `kind`;
- `source` с точными строками и смещениями;
- `parent_id`;
- исходный фрагмент кода;
- `children` для составных конструкций.

Реестр создаётся без участия ИИ. ИИ не может добавлять, удалять или менять эти единицы.

### 2. Последовательные окна

1. Pipeline выбирает область: файл, функция или тело составного блока.
2. Из реестра берётся следующий непрерывный диапазон ещё не обработанных непосредственных единиц. Размер окна определяется доступным контекстом модели, а не фиксированным количеством строк.
3. ИИ получает исходник с номерами строк и явными маркерами `НЕ ОБРАБОТАНО`/`УЖЕ ОБРАБОТАНО`.
4. ИИ возвращает один или несколько блоков. Каждый блок обязан содержать точный список `coverage_ids`, диапазон и русские `label` и `summary`.
5. Pipeline проверяет ответ. Только после успешной проверки единицы помечаются обработанными, и открывается следующее окно.
6. Уже обработанные единицы передаются следующему вызову только как контекст; окончательное состояние хранит машинный реестр, а не текстовая отметка ИИ.

ИИ может объединить несколько соседних единиц в один блок. Блок не может пересекать границы области или включать единицу, которой нет в текущем окне.

### 3. Рекурсивная декомпозиция

Для каждого составного блока (`function`, `if`, `else`, `for`, `range`, `switch`, `case`, внутренний вызов с доступным телом и аналогичные конструкции) pipeline создаёт дочернюю задачу. Дочерняя задача обрабатывается тем же протоколом окон и обязана покрыть все непосредственные единицы внутри родителя.

Родительский блок отвечает за смысл перехода/контекста, дочерние блоки — за каждый шаг внутри него. Листовой блок не требует дальнейшей декомпозиции.

### 4. Строгий валидатор

До генерации DSL проверяются:

- все обязательные единицы покрыты;
- нет единиц вне исходного реестра;
- нет пропусков строк исполняемого кода;
- нет пересечений между блоками одного уровня;
- порядок блоков соответствует исходному коду;
- каждый составной блок имеет полностью покрытые дочерние единицы;
- у каждого блока есть русские `label` и `summary`;
- source-диапазоны и `coverage_ids` совпадают с анализатором.

При любой ошибке pipeline делает ограниченное число повторов с диагностикой валидатора. Если ответ всё ещё неверен, отчёт не сохраняется как готовый: пользователь получает конкретный диапазон и причину отказа. Молчаливый fallback с пропуском строк запрещён.

### 5. Русские описания

ИИ обязан описывать смысл действия, а не копировать идентификатор или условие. Технический код можно показывать в source-информации, но `label` и `summary` должны быть естественными русскими фразами. Для каждого принятого блока оба поля обязательны.

### 6. Визуализация

Объединённые блоки отображаются одной нодой с диапазоном исходных строк. Составные блоки раскрываются через существующую иерархию и полупрозрачные вложенные области. В sidebar остаётся точная ссылка на исходный диапазон.

## Критерии приёмки

- [x] На тестовом файле с присваиванием, стандартным вызовом, условием, циклом и `return` реестр содержит каждую исполняемую AST-конструкцию.
- [x] ИИ может объединить несколько соседних конструкций в один блок, но `coverage_ids` такого блока перечисляет их все.
- [x] Следующее окно получает корректные маркеры уже обработанных единиц и начинается с первой необработанной единицы.
- [x] `if`, циклы, `switch` и внутренние вызовы рекурсивно раскладываются на подблоки.
- [x] Отсутствующий `coverage_id`, пропущенный диапазон или пересечение блоков делает ответ недействительным и не создаёт готовый отчёт.
- [x] Каждый принятый блок имеет русские `label` и `summary`.
- [x] Диаграмма сохраняет порядок исходного кода, source navigation и вложенные scope regions.
- [x] Добавлены unit/integration/E2E-тесты протокола покрытия с замоканным LLM.
- [x] `cargo test`, `cargo clippy --all-targets -- -D warnings`, `CI=true pnpm typecheck`, `CI=true pnpm build` проходят.
- [x] `./scripts/install-mac.sh` успешно переустанавливает Graphloom.
